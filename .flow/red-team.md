# Red-Team: 在空项目落地《Xanthil 本地化数据处理工具 v1.0》（目标 M0+M1）

评审日期：2026-09-30｜评审对象：`.flow/proposal.md`（v1.0 全文 + 两张早期草案图的冲突以正文为准）

## Top Kill-Assumptions (ranked)

### KA1. 模式 S「仅凭 Schema 就能生成正确代码」在真实脏数据上可用
- **Claim:** 云端模型只拿表结构、字段语义、行粒度、指标口径（无样本、无分布、无行数），就能生成可在本地一次或少数几轮内跑出正确结果的 pandas/DuckDB 代码。
- **Steelman:** 现代 LLM 对 pandas/DuckDB 代码生成已高度熟练；分析代码所需信息大部分在 Schema + 口径 + 粒度里；方案还允许「结构性诊断」（字段名、缺失库、语法错误）回传修复，且用户确认口径环节补足了最大歧义源。
- **Fails if:** 在代表性合成业务 CSV 任务集上，3 轮结构性诊断内得到正确结果的比率明显偏低（如 <50–70%），用户体验退化为反复报错却看不到数据相关的失败原因——核心卖点（不用上传数据也能分析）变成核心痛点。
- **Evidence to get this week:** M0 本身：构造 10 个合成任务（含脏类型、前导零 ID、混合编码、退款口径），统计首轮/三轮成功率与失败归因（结构性 vs 数据性）。
- **Kill criterion:** 三轮成功率 <50% → 必须重议模式 S 的上下文构成（例如允许用户显式勾选「本地画像摘要」进入模式 S 上下文，作为介于 S/A 之间的显式授权档），而不是默认继续。
- **Cheapest test:** M0 合成基准（已在里程碑内，无需额外建设）。

### KA2. macOS 上可验证的 Worker 隔离后端在 MVP 周期内可达
- **Claim:** §8.2 要求 OS 级隔离（网络默认拒绝、文件仅授权范围、可杀进程树），且 §17.3 把「目标平台隔离能力未验证」列为发布阻断条件。
- **Steelman:** 方案自己已给出退路：可插拔隔离后端 + 「平台未验证则不开放敏感数据自由执行，用合成数据开发」。M0 退出条件就包含隔离验证，等于把该假设的测试排在最前。
- **Fails if:** macOS（darwin，当前开发机）上找不到能在 M1 窗口内通过 P04（联网阻断）+ P05（越权读阻断）的后端——sandbox-exec/seatbelt 已被 Apple 标记为 legacy，Docker 依赖 VM 且用户未必接受，纯 Python 层拦截不满足「OS 级」。
- **Evidence to get this week:** 一天级 spike：候选后端各写一个逃逸测试（子进程联网 + 读授权外文件 + 写越界路径）。
- **Kill criterion:** 无候选后端同时过 P04/P05 → M1 明确限定「合成/脱敏数据可用，真实敏感数据等隔离后端」，并在 UI/文档标注；不得静默降级。
- **Cheapest test:** 上述 spike；不需要先写完整 Host。

### KA3. 本 flow 预算内只够 M0（+M1 一部分），切片必须狠
- **Claim:** dev-flow 预算 60 轮 / 12h，而方案 §13.2 完整 MVP 是数月工程量（目录、画像、Schema 卡、规划器、Host、持久内核、工件库、可信发布、出站网关、审计、工作台 UI、12 项对抗验收）。
- **Steelman:** 我的目标已收窄为「M0 边界验证 + M1 起步」；M0 是一条细链路（合成 CSV → 结构确认 → 生成代码 → 隔离执行 → 出站捕获），可用 tracer-bullet 垂直切片在预算内打穿。
- **Fails if:** ISSUES 拆解出的切片数 × TDD 成本超出预算，导致 VERIFY 阶段大量未验证代码；或为赶进度跳过 P 系列对抗测试，违背 §17.3 发布阻断。
- **Evidence to get this week:** ISSUES 阶段按切片估算规模；每片必须带可运行验收。
- **Kill criterion:** 切片总量超出预算 2 倍 → 收缩为「M0 完整闭环 + M1 的 Catalog/内核最小版」，M1 其余移出本 flow，记录到 tasks.md 待续。
- **Cheapest test:** 拆解本身就是测试。

### KA4. 开发环境存在可用的模型 API 凭据（供 M0 真实链路演示）
- **Claim:** M0 要「Agent 生成代码」，需要至少一个真实可调的云端模型端点。
- **Steelman:** 工具侧可以做 Provider 抽象 + 环境变量注入密钥；测试用 fixture 回放，不依赖真实凭据；用户是 GLM 生态重度用户，大概率有可用 key。
- **Fails if:** 用户环境中没有任何可用凭据，M0 只能以「录制回放」方式演示生成环节。
- **Evidence to get this week:** 检查环境变量/配置中是否存在模型凭据（只查存在性，不读值）。
- **Kill criterion:** 无凭据 → M0 以 fixture 驱动完成全链路 + 真实调用留一个手动冒烟脚本，交由用户自行填 key 运行；不阻塞 flow。
- **Cheapest test:** `env | grep -c` 存在性检查。

### KA5. 持久内核 + 版本失效机制的复杂度在 M1 可控
- **Claim:** M1 需要 jupyter_client/自建协议的持久 Python 内核，支持跨轮复用与数据版本失效（F05/F06）。
- **Steelman:** 方案已把持久内核放 M1 而非 M0；且「串行可变执行 + 版本绑定失效」把最难的状态污染问题预先约束住了。
- **Fails if:** 内核生命周期/中断/重启的状态机 bug 吞掉 M1 大部分预算（这类基础设施调试成本高且不产出用户可见价值）。
- **Evidence to get this week:** M0 先用「一次性子进程执行」验证最小执行路径，M1 再引入持久化，观察 M0 执行适配层抽象是否真的可替换。
- **Kill criterion:** 持久内核切片预估 >8 个 TDD 任务 → 改为「进程内 pandas 会话对象 + 显式 restart」的降级实现，Jupyter 协议后置。
- **Cheapest test:** M0 执行抽象的设计评审（接口先行）。

## What's Well-Reasoned

- **模式 S/A 二分取代「暴露等级 Level 0–3」是正确升级**：旧图把「完整上下文」列为默认最高档，v1.0 明确弃用并区分「不出本机 / 不上传原始记录 / 不进入模型」三个常被混为一谈的概念——这在同类「本地隐私」产品宣传里少见地诚实。
- **可信发布 = 按批准计划在同版本数据上重算聚合，而非正则/LLM 过滤任意输出**：这是技术上唯一站得住的做法（任意 Python 输出不可证明安全，一个浮点数也能编码敏感值——方案 §8.4 自己点破了）；「不允许用另一个云端 LLM 判敏感」同样正确。
- **引用事实核对过且用法克制**：DuckDB 非沙箱、Jupyter 多输出通道、Prime Agent Worker 非安全边界——都被用作设计约束而非营销背书。
- **发布阻断条件（§17.3）和对抗验收（P01–P12）先行定义**，使「安全声明」可被工程验证，而不是上线后补。
- **里程碑 M0 即 KA1/KA2 的直接测试**——方案结构与假设风险对齐，无需额外造验证项目。

## What I Couldn't Assess

- Xanthil Desktop 集成点（M3）：该仓库不在当前工作区，无法核对「复用现有会话/模型配置」的实际接口——本 flow 不做 M3，风险后置。
- 云端模型对「无样本 Schema」代码生成的真实成功率：只有 M0 基准能回答（KA1）。
- 用户环境模型凭据可用性（KA4）。
- Windows/Linux 隔离后端：本机为 darwin，其他平台无法在本环境验证。
- 性能目标（§14.3）方案刻意未定数值，属后续基线工作，本轮不评估。

## Verdict

**go** — 无任何 kill 准则已被满足。方案自我风险意识强（预答了多数攻击），最脆弱的两个假设（KA1 模式 S 可用性、KA2 macOS 隔离）恰好是 M0 的退出条件，先测最便宜的致命假设，符合红队排序原则。进入 PRD。
